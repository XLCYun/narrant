# 原生语言分析辅助进程：接口设计讨论

日期：2026-10-02。状态：共同架构与单图并集语义已确认；配置发现暂定。后续工程草案见 [0024 公共协议](../specs/0024-native-analyzer-helper-protocol.md) 和 [0024a 语言配置与验收](../specs/0024a-native-language-analysis-profiles.md)；后端实现和兼容矩阵尚未验收。

## 已确认方向

- Java、Go、C#、C/C++ 采用原生分析辅助进程，通过通用接口提供构造 Code Graph 所需的信息；辅助进程负责语法与语义分析，不强制再接一套 LSP/语言服务器。
- 辅助进程负责语言特有对象分类、内容投影、稳定身份、图成员和关系分类，返回规范化构图数据；Rust 负责输入/来源边界、协议、公共校验、最终 CodeGraph 构造和生命周期。
- 当前 Rust、TS/JS、Python 实现保持不动；新实现验证其清晰性与可维护性后，再单独决定是否迁移现有语言。
- 四类新语言统一不执行被分析仓库及依赖携带的构建脚本、插件、注解处理器和生成器；Java 完整构建导入、C# MSBuild 设计时导入均不属于实施路线。
- 首版语义上下文参照现有默认范围：本侧仓库源码 + 明确目标平台的标准库/参考声明。不为分析下载、restore 或 install 项目依赖，也不自动纳入用户机器上已有的第三方依赖环境或缓存。
- Q5 已确认：在最终选定的配置与源码范围内，对象提取完整时允许关系为 Unresolved；对象无法完整提取则明确失败，首版不增加部分结构图模式。这不等于 Q4 已选定单配置范围。
- Q6 已确认：对外只返回一张配置并集代码图，对象与已解析关系表示“至少一种已分析配置下存在/成立”；输出不保留逐事实配置归属，不做配置切换或变体界面。无法正确归并的对象/结构按 Q5 明确失败。
- 架构选择记录于 [ADR-0034](../adr/0034-use-native-analyzer-helpers-for-new-languages.md)。它没有批准具体引擎版本或未验证的兼容性承诺。

## 暂定方向

用户对 Q4 答复“先暂定按推荐来，看看后面还会不会遇到其它问题”：自动识别项目中静态可确定的明确配置，在各配置下分别分析，再汇总展示。默认不要求用户逐配置操作，也不把互斥源码放入同一次类型检查；不承诺穷举任意宏、构建标签或未知脚本产生的全部配置。

这是继续设计的前提，不是已经验证可实现的承诺。若对象身份、条件关系、性能或现有接口兼容性暴露冲突，应重新讨论 Q4，不能为了保留暂定方案悄悄丢弃配置、对象或关系。

## 术语与现有契约

沿用 [CONTEXT.md](../../CONTEXT.md) 中的 Code Object、Code Object Content、Code Graph、Code Relationship 和 Language Support Pack，并记录已确认的 Configuration Union Code Graph（配置并集代码图）。Code Graph 是一个固定比较侧、选定文件范围内的代码对象与关系，并非编译器 AST；并集语义不表示每项事实在所有配置下成立，也不证明任意组合能在同一配置中同时成立。

“辅助进程”“进程协议”“构图 DTO”属于实现概念，记录在设计文档，不加入领域词汇表。

- [LanguageAnalyzer](../../src-tauri/src/structure_review/code_graph/analyzer.rs) 规定分析输入及返回 CodeGraph，没有强制 LSP 或现成的跨进程序列化协议。
- [节点模型](../../src-tauri/src/structure_review/code_graph/node.rs) 将稳定身份编码、签名规范化和独立子对象内容投影交给语言实现。
- [CodeGraph 构造](../../src-tauri/src/structure_review/code_graph/graph.rs) 和 [校验](../../src-tauri/src/structure_review/code_graph/validation.rs) 负责公共图约束；[差异比较](../../src-tauri/src/structure_review/code_graph/diff.rs) 不负责解释各语言 AST。图结构合法不等于语言语义、选集完整性或内容规范化已经正确；这些仍需各语言的适配与验收。
- 原生后端是否在 Rust 进程外，不改变选中文件决定图成员、其他源码可作为上下文、Node/External/Unresolved 区分和不能把分析失败伪装为空图的既有约定。

## 决策树

```text
├─ Q1 输出边界：辅助进程返回规范化构图数据【已确认】
├─ Q2 执行边界：四类语言统一不执行项目构建逻辑【已确认】
└─ Q3 输入范围：仓库源码 + 目标标准库，不加载第三方依赖环境【已确认】
   ├─ Q4 同文件多配置：自动识别明确配置，分别分析后汇总【暂定，允许复议】
   │  └─ Q6 汇总表达：单张配置并集图，不保留配置归属【已确认】
   │     └─ 技术验证：兼容对象归并、关系并集、配置来源与缓存正确性
   └─ Q5 对象提取不完整：明确失败，不新增部分结果模式【已确认】

后续：通用协议草案、目标平台提供方式、语言支持矩阵与实施验收。旧的逐配置结果封套、变体界面和配置增减专门展示不再作为默认待办。
工作区所有权、子进程完成后才释放工作区等既有契约直接保留，不重复决策。
```

### Q1：辅助进程输出到什么层级？

**已确认，按推荐采用：** 辅助进程完成语言特有的对象分类、内容规范化、稳定身份、图成员判定和关系解析，返回符合通用契约的构图数据；Rust 负责输入/来源边界、协议解码、公共校验和 CodeGraph 构造。通用接口统一结果语义，不统一编译器内部 AST。

未采用的替代方案：辅助进程返回较底层声明/符号证据，Rust 中各语言适配器继续完成投影与身份映射。这样 Rust 持有更多规则，但每门语言的逻辑跨越两个实现语言和进程边界。

四份调研的早期责任分配建议并不完全一致，本决定统一其边界。例如 C/C++ 原建议 Rust 侧执行成员判定及身份映射，现改为 helper 负责；Go 原已提出 helper 内含身份和规范化输出模块。协议的字段和编码尚未冻结。

### Q2：是否统一禁止执行被分析仓库的构建逻辑？

**已确认，按推荐推广：** 四类新语言不执行被分析仓库及其依赖携带的构建脚本、插件、注解处理器或源码生成器。受控分析工具的启动与执行仓库逻辑分开判断；静态读取配置或已有允许范围内元数据不等于执行构建。

代价是不能承诺完整还原任意 Gradle、MSBuild 或其他动态项目配置，也不会凭空得到未存在的生成代码。允许的读取操作是否只读仍须实测，不能由“不运行构建”直接推出。

C# MSBuildWorkspace 设计时导入会执行项目 targets，故不是批准的实施路径；Go 等项目加载工具也须证明不执行被排除的逻辑并满足工作区约束，不能因为入口叫“分析”就豁免。

### Q3：语义分析允许读取哪些依赖？

**已确认，按用户纠正收窄：** 参照已有默认语言支持，只使用本侧仓库源码与明确目标平台的标准库/参考声明，不为分析下载、restore 或 install 项目依赖；不因为用户机器上已经存在依赖缓存、JAR、NuGet 包或安装环境就扩大语义上下文。

撤回原先“允许明确提供的已有第三方库”作为首版推荐的提议。仓库内源码及必要静态配置如何识别按各语言规则确定，不能把安装目录自动当作快照源码。支持包下载与项目依赖下载是不同边界，目标 SDK/参考声明的具体提供方式尚待细化。

核查依据：

- [Rust 规格](../specs/0019-rust-language-analyzer.md) 的默认 `standard-library` 排除项目依赖并强制 Cargo 离线；[实际启动配置](../../src-tauri/src/structure_review/rust_analyzer/lsp.rs) 与之相符。已有显式 `all-dependencies` 模式允许项目依赖并继承 Cargo 网络配置，保持不动，不能声称现有所有模式均不下载。
- [TS/JS 规格](../specs/0021-typescript-language-analyzer.md) 默认排除业务依赖源码与声明，关闭 ATA；[文件宿主](../../src-tauri/src/structure_review/typescript_analyzer/runtime/workspace.mjs) 控制可见范围，即使 node_modules 已存在也不默认纳入。固定平台类型声明属于允许的标准环境。
- [Python ADR-0033](../adr/0033-bound-python-analysis-to-repository-and-standard-library.md) 和 [会话启动](../../src-tauri/src/structure_review/python_analyzer/session.rs) 排除用户解释器、venv、site-packages 及第三方依赖发现。

共同原则继续有效：关系能否确定必须依赖证据；只缺语义时保留可确认对象及 Unresolved。若连源码对象完整性都无法保证，不能把不完整输出标为普通成功图。Q5 已确认首版不增加部分结果模式。

## 配置分析与单图输出的决定

### Q4：同一源码的多个构建配置如何处理？

例如 C/C++ 条件编译、Go build tags、C# 不同目标框架会使同一文件在不同配置下具有不同声明或绑定。

原建议首版只分析一个明确目标配置，以控制成本；用户追问能否一起分析后，**暂定改为自动识别明确配置、分别分析、汇总展示**。before/after 使用一致的配置发现与选择规则，各自读取本侧源码与配置；不把不同配置的事实解释为同时无条件成立。

逐配置产生分析结果是内部手段；Q6 已决定对外单图并集，不保留配置归属。声明差异必须能正确映射到既有源码对象契约，否则明确失败；未活动分支的覆盖没有因此自动得到保证，范围必须相对于明确配置集合解释。

**用户追问：是否可以不处理配置、一起分析？** 这需要区分用户是否必须手动选择配置，与分析器是否需要理解配置。批量分析所有选中文件本来就可以；但互斥条件分支、平台文件和目标框架不一定能放入同一次类型检查。例如 Go 的 `platform_windows.go` 与 `platform_linux.go` 可以分别声明同名平台函数，丢掉文件选择规则会制造重复声明；C/C++ 的条件分支还可能改变语法使用的类型和宏。

曾比较自动识别单配置、多配置分别分析和跨分支源码结构三类方案。当前按必要上下文取得证据后生成并集；后台仍须处理源码身份和内容兼容性，但不把关系条件输出为公共字段。仅忽略条件并标 Unresolved 不能弥补漏掉的源码对象。任意宏组合未必有限且可发现，不能把若干已知配置的覆盖声称为所有可能配置的完整覆盖。

用户先暂定自动识别明确配置、分别分析，随后确认 Q6 的单图并集输出。这些答复没有批准修改 CodeGraph 的具体字段、复制配置节点来回避内容冲突、将已确定关系一律降为 Unresolved，或在某个配置失败时返回剩余配置的成功部分结果。

### Q5：对象提取不完整时是否新增部分结果模式？

缺第三方依赖不一定只影响关系。尤其 C/C++ 缺少头文件时，类型、宏或声明本身都可能解析不完整。

**已确认，用户答复“5 ok”：** 首版维持既有完整图契约：对象完整、部分关系不确定时使用 Unresolved；无法保证所选配置与范围内对象完整时明确失败。不增加“部分结构图”产品模式。

未采用的替代方案是新增明确标识的部分结果模式，并重新定义如何显示遗漏和比较两侧不同的可解析范围。配置与分支的承诺范围仍由 Q4 决定，不能借 Q5 默认排除未活动源码。

### Q6：单图并集（已确认）与未采用方案

**已确认，用户答复“ok”：** 对外单张图表达至少一种已分析配置下存在的对象及关系，不保留逐事实配置归属。后台仍按语言要求建立分析上下文，再归并兼容的源码对象与已证实关系；不是删除条件后让编译器把所有代码同时启用。

**代码核对事实：** 当前节点只有一份 `signature`/`code`，引用只有 `semantic` 与 `target`；`CodeGraph::merge` 拒绝重复 NodeId，并不是多配置归并器。节点 `extensions` 参与自身内容比较，不能仅在其中塞配置条件却继续把关系当作无条件集合比较。

此前建议的产品行为（未批准）：同一源码声明在汇总列表中只出现一组；各配置内容一致时折叠，不同时可以展开对应变体。关系保留“在哪些已分析配置下成立”，不同配置解析到不同目标不等于目标未知；只有配置内证据不足才使用 Unresolved。用户随后质疑这会使设计复杂，故不继续把变体展示作为默认实施前提。

此前配套的内部路线（未批准）：每配置保留一张完整 CodeGraph，通过明确的配置结果容器组织，再在结果/展示层按可证明的源码对应关系归组。单配置内继续复用现有六类对象、单父树、身份约定、校验和 diff。不要把配置摘要直接拼进源码对象 ID，也不要拼接多个配置的代码正文。

逐配置结果容器会需要新的跨配置对应与应用层契约，因此未采用为首版路线。现有 `LanguageAnalyzer` 返回单个 CodeGraph，[StructureComparison](../../src-tauri/src/structure_review/application/projection.rs) 承载 before/after 两张图；单图并集方向保留这一结果形态，现有三种语言无需为了配置展示迁移。具体实现仍须验证协议和对象映射，不能把方向相容说成实现已完成。

另一未采用路线是将 CodeGraph 本身扩展为条件图：节点内容、包含关系和引用关系都支持适用配置，并同步修改公共校验和 diff。其影响范围更大；已接受的单图并集不要求这些条件字段。

用于检验的场景：同一个 `run()` 源码调用 `use(n)`，配置 A 下 `n` 的类型是 int、调用 `use(int)`，配置 B 下是 long、调用 `use(long)`。并集可以保留两条已确定目标的调用边，含义是它们各自在至少一个已分析配置中成立；不表示同时执行，不仅保留第一项，也不一律降为 Unresolved。源码声明的对应关系需证据，不能只按同名归组。

**表述修正：** 当前静态 `code.calls` 并不表示运行时必然执行，出现两条调用边也不自动表示两次调用同时发生。上段的“同时调用”不能作为拒绝并集图的理由；准确的限制是不能把只在某配置中解析成立的事实，冒充在每一种配置下都成立。若明确约定每条边表示“至少一个已分析配置中观察并解析到的调用”，关系并集可以有明确含义。

本项语义已批准，术语已记入 CONTEXT.md。配置来源与配对仍可作为内部分析和缓存证据，首版不做配置增减的专门展示；消息字段和具体编码仍待协议设计。

### Q6 追问：是否可以忽略配置，把所有情况合成一张图？

用户明确担心复杂度，并询问这是否来自 LS 不允许同时分析多个配置。**核实事实：** 不是 LSP 的统一禁令。[gopls 工作区文档](https://go.dev/gopls/workspace) 说明它可以同时维护多个构建上下文，但一次引用等查询通常仍使用该文件的默认构建，并不遍历所有可能配置；[clangd 编译命令文档](https://clangd.llvm.org/design/compile-commands) 则说明解析需要每文件的语言、目标和预处理等上下文。原生 helper 同样要满足语言语义，不能靠绕过 LSP 让互斥声明同时成为合法程序。

应区分三件事：

1. 普通运行时 `if` 的两支通常都参与语义分析，调用图可以同时记录其中的调用。
2. 预处理条件、平台文件选择和目标框架可能决定输入有哪些声明、宏和类型；不能简单去掉这些规则后期待编译器得到正确绑定。
3. 分别取得可信结果后，可以定义一个单图并集：保留在至少一个已分析配置中存在的源码对象和已解析关系，界面不展示配置变体。这不等于关系在每种配置下都成立，也不证明任意关系链能在同一配置下成立。

**已批准的简化方向：** 单图并集，不引入多配置切换/变体界面。源码内容保持源码表达，不拼接不同编译结果的签名或对象布局。已解析关系并集只收纳有后端解析证据的事实，不按同名符号猜测；只对明确已分析的配置集合承诺覆盖。

该方向尚有结构层限制：一个源码声明可能在不同配置下有不同类别、内容或包含位置，而现有 NodeId 只有一份节点数据。需要验证源码投影与身份是否能无冲突表达；无法表达时按 Q5 明确失败，不能任选一份覆盖或把结构缺失藏进 Unresolved。若需要扩大模型处理这些冲突，再以具体反例讨论，不在本轮默认为已批准条件图或变体模式。

用户已确认接受“至少一种已分析配置下存在/成立”的单图并集，并放弃配置归属展示。该结果语义不扩大到所有可能配置，也不允许缺少证据的猜测目标。

**Q5 对暂定 Q4 的约束：** 任一已纳入配置的对象提取失败，不能仅返回其余配置并标为完整成功。已发现会影响选集却无法解释的配置也不能悄悄忽略。没有项目配置时是否采用明确的独立文件配置，与发现了无法解释的项目配置是不同情形；前者依赖后续目标平台/语言支持矩阵，不在本轮预设默认值。

## 归并必须满足的既有约束

- 先按可证明的源码身份归并对象，再确定最终图成员；同名不等于同一对象，配置摘要不能用来制造绕过冲突的节点副本。
- 同一身份的类别、自身内容、语义扩展和声明位置必须兼容；包含关系并集仍须满足单父、无环和根可达。无法正确表达时失败，不能取第一份或拼接互斥内容。
- 以最终并集成员集合重新判定 Node/External；有确定声明身份但未入图才是 External，不能按名字将图外目标升级为 Node。
- 某配置的确定目标不能自动消除另一个配置的未知绑定；保留有证据的已解析关系与仍未知的观测，不能把“某处已解析”误当“全部观测均已解析”。
- before/after 沿用相同范围政策、工具版本、身份与规范化约定，各自读取本侧源码/配置。仅配置名称或内部顺序变化而最终图未变，不构造假的对象变化；真实并集事实变化按现有 diff 表示，不声称因此证明运行行为变化。
- 以上是已定结果语义及图契约的实现约束，不增加配置 UI、业务依赖读取或部分成功模式，也不改变现有三门语言的处理方式。

## 后续技术工作

通用进程协议已起草于 [0024](../specs/0024-native-analyzer-helper-protocol.md)，语言 profile 与验收入口见 [0024a](../specs/0024a-native-language-analysis-profiles.md)。后续验证跨配置的源码对象归并、只读项目加载、目标标准库与进程回收。具体目标平台、语言版本、无项目配置时的支持策略和各语言对象粒度归入语言规格，不把尚未运行的探针当作验收通过。若验证要求改变本轮已定语义或扩大执行/依赖范围，再回到对应产品决定；本轮未实现业务代码。
