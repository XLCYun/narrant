# 当前桌面上的隔离升级验收

用户已于 2026-10-16 同意：使用独立的 Narrant Upgrade Test 验证安装与升级，正式包单独验证签名和完整性，并如实调整规格中的证据范围。继续使用现有 macOS/Windows runner、账户和登录会话，不操作日常 Narrant。

后续决定：旧版 macOS 实测暴露两平台共用的下载编号缺陷，修复后用户要求暂停 macOS 升级测试，
只继续 Windows。当前 Windows 分支回归用同一修复源码构建两个测试版本，明确不作为旧 Stable
升级成功或正式发布资格；原旧版失败保留。普通 macOS 质量检查与 E2E 继续。

## 实现边界

- 旧版取上一 Stable 的源码，新版取待验收源码。只叠加可审查的测试身份、内存凭据和数据观察入口；更新器、暂存、退出和平台安装实现使用各自版本的原代码。记录源码 SHA、叠加差异和两份测试包摘要。
- 独立名称、bundle identifier、主程序名、NSIS 安装记录和数据目录；不使用正式产品的安装目录。缺少隔离配置时在启动插件和读取数据前失败。
- 测试包使用本次生成的 updater 签名密钥；macOS 测试 app 使用 ad-hoc 代码签名。正式包的真实 updater 签名、Developer ID、公证和摘要另行核验，不能将测试包启动结果当作正式包的 Gatekeeper 或升级结果。
- 使用仅传给测试进程的 HTTPS_PROXY 与 SSL_CERT_FILE，服务固定 HTTPS 更新域名与包路径。不给系统安装 CA，不修改 hosts、系统代理或日常账户钥匙串。
- 旧版通过应用接口写入一个临时 Git 项目及主题/语言设置；新版只读回这些数据并比较。不得启动时重新写入夹具来掩盖数据丢失。
- 两平台真实运行安装、检查、下载、验签、持久化暂存、正常退出安装、原路径替换、手动重启与数据保留。证据明确标记 isolated-native，并分别绑定测试包与正式包。

## 执行顺序

1. 共用测试凭据隔离与最小数据观察入口，建立独立 Tauri 打包配置。
2. 用进程级 TLS gate 替换系统 hosts/证书适配器；验证真实 TLS、限定路由和失败清理。
3. 构建两份可溯源测试包，调整平台适配器、数据保留断言与证据校验。
4. 接入现有 runner 与发布门禁；分支验收可以没有正式 Draft，此时明确不产生发布资格。
5. 本地聚焦检查后，普通质量检查与 E2E 完成两平台 CI；升级测试按用户最新决定只运行 Windows。同步规格、运维文档和 PR；旧提交的失败结果独立保留。

## 验收限制

隔离包验证升级实现和模拟数据保留，不能保证正式产品身份、真实安装目录和生产签名组合下不存在问题。正式包静态核验不能补成“正式包本体完成升级”的结论。本轮不发布版本、不创建生产标签。
